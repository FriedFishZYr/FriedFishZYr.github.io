Boston University RASTIC · Learning product case study

Making robot code visible to beginners

MeArm Classroom Motion Lab links beginner Arduino commands to a 3D motion preview, so students can predict, explain, and revise before testing on hardware.

STEP 01Classroom problem

A code change had no visible payoff

Students could move the arm by hand, but struggled to see why writing code mattered. Small coordinate changes were hard to observe, and the coordinate system was unfamiliar. The team’s first simulator attempt could not compile the MeArm library.

Design question

How can beginners see what a command will do, connect it to motion, and understand why a coordinate fails?

    learners in the cohort that used the preview

  • 4

STEP 03Decision 1 · Scope as a scaffold

Support the first coding lesson only

I scoped the two-week build to the lesson’s sequential motion, claw, and delay calls. Pasted code is parsed, never executed.

In scope

  • begin, moveToXYZ, snapToXYZ
  • openClaw and closeClaw
  • delay
  • Comments and pin declarations

Left out

  • Loops and conditionals
  • Variables in movement calls
  • Custom functions
  • Arbitrary Arduino APIs

Tradeoff

No loops, variables, or custom functions. Students eventually outgrow the subset.

The intended lesson loop. Starter prompts support prediction; source-linked commands and stepping support explanation. These are design intentions, not measured learning gains.

  4. 04

  5. 05

    Check the boundary

    Read the diagnostics, then verify the motion on hardware.

STEP 05Decision 2 · Make uncertainty visible

Show what the model can and cannot check

Source-linked diagnostics expose reachability and servo-limit failures on the line that caused them. A failed parse disables playback, so a stale preview can never run.

    Caution

    Playback continues

    Reachable, but not an approved pose. The preview still plays; verify the pose on hardware.

  • Line 13: Position exceeds the configured shoulder servo limit.

    Invalid

    Timeline truncates

    The timeline stops before the invalid motion. Revise the coordinate and preview again.

    Code error

    Playback disabled

Tradeoff

Kinematics and timing do not establish physical safety. The preview does not model collisions, torque, heat, or backlash.

STEP 06Decision 3 · Iterate on the arm model

The arm model took two builds to get right

The 3D arm is what students compare their predictions against, so it has to look like the kit on their desks.

The first build ignored the documented part dimensions and assembly order. I scrapped it and rebuilt the model from the MeArm reference geometry, then locked it in with eleven arm-model tests that check transforms and part ordering, so later changes can’t quietly break it.

Tradeoff

Reference-matched graphics still need comparison with a calibrated physical arm.

STEP 07In the classroom · one instructor-reported episode

From a stalled rescue task to a completed pickup

  1. Difficulty

  2. →

  3. Tool use

    Students planned the sequence in the viewer and inspected it with the scrubbable timeline.

  4. →

  5. Observed result

    They returned to the physical arm and completed the pickup. The tool served as a planning reference.

What this episode does not show

The tool’s effect was not isolated. Instructors still rated the programming introduction “so-so”; IDE setup and uploading consumed much of the day.

STEP 08Evidence and limits

What this does and does not prove

  • Software evidence

    A working release candidate

    57 automated tests pass, alongside strict type checking, a production build and an offline-asset check. Final browser and hardware gates remain open.

  • Classroom evidence

    Use observed in one cohort

    Six learners used the preview. One reported episode shows its use as a planning reference.

  • Learning evidence

    Outcomes remain unmeasured

    No assessment or comparison establishes gains in understanding, speed, or independence.

Release boundary: v0.9.0. Final browser checks and the physical validation protocol are required before a classroom-ready 1.0.

STEP 09Next iteration · proposed, not implemented

Clearer errors, then a learner evaluation

  1. 01

    Give beginners an actionable message

    The loop example reports “Unsupported character '<'.” It should explain that loops are unsupported and suggest a sequence of explicit commands.

  2. 02

    Run a small beginner evaluation

    Think-alouds with 4–6 beginners to examine predictions, explanations and error recovery, and to investigate the IDE setup and upload bottleneck instructors reported.
